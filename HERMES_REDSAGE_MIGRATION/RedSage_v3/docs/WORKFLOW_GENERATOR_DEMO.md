# RedSage v3 Workflow Generator Demo

## Source problem statement

**Source:** PortSwigger Web Security Academy, “User ID controlled by request parameter” lab:
https://portswigger.net/web-security/access-control/lab-user-id-controlled-by-request-parameter

**Scope note:** This is a deliberately vulnerable PortSwigger training lab. It is not authorization to test any real target. The following is a roadmap-ideation demonstration only.

## Problem statement

The lab describes a horizontal privilege-escalation issue on a user account page where the user identity is controlled by an `id` request parameter; the learner is instructed to use the supplied lab account and determine whether another lab user’s account information is exposed.

## Workflow generator result

### 1. Classification

- Primary class: authorization / horizontal access-control testing.
- Secondary class: object-level authorization and identifier-controlled resource access.
- Environment: lab-only.
- Confidence: high, because the problem statement explicitly identifies the lab environment and the user-controlled identifier.

### 2. Authorization and safety gate

- Proceed only against the PortSwigger-provided lab instance.
- Do not transfer the same test to an unrelated domain or production target.
- Use only the supplied lab account and lab data.
- Do not access or retain unrelated personal information.
- Stop if the task requires testing outside the lab scope.

### 3. Clarification questions

For this lab statement, no blocking clarification is required, but the generator would ask these questions for a real engagement:

1. What exact hostnames or application instances are authorized?
2. Are horizontal access-control tests explicitly permitted?
3. Which test accounts may be used?
4. What data must not be accessed or retained?
5. What rate and operational limits apply?
6. What evidence and report format are required?

### 4. Initial roadmap

#### Phase 1 — Understand the authorized context

- Record the lab URL and supplied account conditions.
- Identify the stated objective: determine whether object access is bound to the authenticated user.
- Record the allowed test boundaries and stop conditions.

Expected evidence:

- Lab/problem statement.
- Scope record.
- Test-account identity.
- Timestamped notes.

#### Phase 2 — Establish the normal user flow

- Manually authenticate to the authorized lab.
- Navigate to the account page through the normal interface.
- Record the request shape and the identifier used to select the account resource.
- Capture a minimal sanitized request/response pair.

Expected evidence:

- Request path and parameter name.
- Response status and relevant non-sensitive fields.
- Account context used for the baseline.

#### Phase 3 — Check object-level authorization

- Form the hypothesis: the server may trust a client-supplied object identifier without enforcing ownership.
- In the lab only, compare the behavior of the authorized test account’s identifier with the lab-provided alternate identifier.
- Observe whether the application returns another user’s account data.
- Do not enumerate arbitrary identifiers or collect unnecessary data.

Expected evidence:

- Baseline request.
- Controlled comparison request.
- Response difference limited to the minimum necessary proof.
- Sanitized evidence showing whether authorization was enforced.

#### Phase 4 — Validate and rule out false positives

- Confirm the response is generated by the target application, not a cached or generic error page.
- Confirm the account context and identifier are correct.
- Repeat only as needed within the lab’s rules.
- Determine whether the behavior is horizontal access, a non-sensitive public record, or an intentional lab feature.

Expected evidence:

- Reproducible response behavior.
- Minimal affected object description.
- Clear distinction between authenticated user and requested object.

#### Phase 5 — Document the result

If the behavior is confirmed in the lab:

- Classify it as an object-level authorization weakness / IDOR-style issue.
- Record affected functionality and data exposure.
- Avoid claiming real-world impact beyond the observed lab behavior.
- Map to the relevant CWE/OWASP category with a citation.
- Draft remediation: enforce server-side authorization against the authenticated principal and requested object.

### 5. Stop conditions

Stop and ask for human clarification if:

- The target is not the authorized lab instance.
- The alternate identifier is not supplied or permitted by the lab.
- The test would expose real personal or confidential data.
- The activity would require enumeration beyond the stated objective.
- The result suggests account takeover, destructive action, or access beyond the lab task.
- Authorization or rules are unclear in a real engagement.

### 6. Human approval gates

- Approval before applying this roadmap to any real target.
- Approval before expanding from one controlled comparison to broader testing.
- Approval before recording a finding as confirmed.
- Approval before sending or publishing a report.

## Demonstration conclusion

The workflow generator converts a compact problem statement into a gated roadmap: classify the issue, confirm the environment, establish a baseline, test one controlled authorization hypothesis, capture minimal evidence, check false positives, and document the result without expanding scope or executing attacks automatically.
