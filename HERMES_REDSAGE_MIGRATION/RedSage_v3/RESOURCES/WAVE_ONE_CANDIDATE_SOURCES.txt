REDSAGE v3 KB — WAVE ONE CANDIDATE SOURCE APPROVAL LIST
========================================================

Status: PROPOSED ONLY — DO NOT DOWNLOAD OR INGEST UNTIL OPERATOR APPROVES
Purpose: Candidate sources for a workflow-roadmap KB that interprets an
authorized web-application pentesting question or bug-bounty problem statement
and produces clarification gates, ordered phases, hypotheses, tasks, evidence
requirements, stop conditions, and citations.

IMPORTANT LICENSING RULE
------------------------
GitHub availability does not prove that a book, document, repository, dataset,
or write-up may be commercially redistributed or embedded in a paid hosted
service. Before download/ingestion, record the exact license, repository commit
or document revision, attribution obligations, ShareAlike/copyleft conditions,
and any commercial-use restriction. A source without confirmed rights is
REVIEW-ONLY until permission or a legally safe paraphrase decision exists.

IMPORTANT SAFETY RULE
---------------------
We will digest methodology, reasoning, scope, evidence, validation, reporting,
and remediation material. We will not ingest executable code, credentials,
secrets, malware, destructive payloads, persistence content, or unauthorized
attack automation. Tool documentation is deferred to Wave Two.

========================================================
A. PRIMARY METHODOLOGY BOOK — OPERATOR TO PROVIDE
========================================================

Candidate:
- One book selected and uploaded by the operator, focused on bug hunting,
  penetration-testing methodology, web assessment, or structured security
  problem-solving.

Preferred characteristics:
- Legally obtained source file or official publisher/author release.
- Clear commercial-use permission, or permission for internal/private use with
  a separate decision for hosted subscription redistribution.
- Strong coverage of engagement preparation, scope, reasoning, validation,
  evidence, reporting, and remediation.

Why digest it:
- Core roadmap sequencing and problem-solving logic.
- Chapter/section/page citations.
- Initial phases, tasks, Steps, prerequisites, and completion criteria.

Approval needed:
- Exact title, edition, author, source, and usage rights.
- This is the first resource to process; do not assume a pirated GitHub copy is
  acceptable.

========================================================
B. OWASP OFFICIAL REPOSITORIES — APPROVE FOR WAVE ONE
========================================================

B1. OWASP/wstg
Candidate resource:
- OWASP Web Security Testing Guide repository.
Digest:
- Testing categories, objectives, prerequisites, expected observations,
  evidence/reporting structure, and section citations.
Use:
- Map a web-app problem statement to recognized testing areas.
- Build roadmap branches without treating category matches as proof.

B2. OWASP/ASVS
Candidate resource:
- OWASP Application Security Verification Standard repository.
Digest:
- Verification requirements, control families, authentication/session/access
  control expectations, and versioned requirement identifiers.
Use:
- Define what should be verified and what evidence supports a control claim.
- Support defensible report references.

B3. OWASP/Top10
Candidate resource:
- OWASP Top 10 repository, selected current release only.
Digest:
- High-level risk categories, definitions, and references.
Use:
- Initial problem classification and prioritization.
- Not a standalone testing procedure and not proof of a finding.

B4. OWASP/CheatSheetSeries
Candidate resource:
- OWASP Cheat Sheet Series repository, selected web-app sheets only.
Initial selection:
- Authentication, Authorization, Session Management, Input Validation,
  Threat Modeling only if approved for Wave One, Error Handling, Logging,
  Secure Headers, and Vulnerable Dependency Management.
Digest:
- Defensive control expectations, validation guidance, and remediation.
Use:
- Improve hypotheses, expected evidence, and remediation recommendations.

B5. OWASP/API-Security
Candidate resource:
- OWASP API Security Top 10 repository.
Status:
- DEFERRED unless the operator expands Wave One from web apps to APIs.
Reason:
- Keep the first retrieval evaluation focused on web applications.

C. WEAKNESS AND SEVERITY REFERENCES — APPROVE FOR WAVE ONE
========================================================

C1. MITRE/cwe
Candidate resource:
- Official CWE data and relevant web/application weakness entries.
Digest:
- Weakness IDs, definitions, relationships, mitigations, and references.
Use:
- Normalize observations and hypotheses.
- Link findings to weakness classes without automatic confirmation.

C2. FIRSTdotorg/cvss
Candidate resource:
- Official CVSS specification/calculator guidance, exact version only.
Digest:
- Severity vector meanings, impact/exploitability concepts, and scoring rules.
Use:
- Make severity reasoning consistent and explainable.
- Never infer a score from a taxonomy match alone.

C3. NVD data
Candidate resource:
- Only targeted NVD/CVE records relevant to selected web technologies, not the
  entire feed for Wave One.
Status:
- CONDITIONAL APPROVAL.
Use:
- Technology-specific context, known affected versions, and references.
Risk:
- Staleness, scale, and irrelevant retrieval noise.

G2. Vendor security advisories
Candidate sources:
- Official vendor advisories relevant to web applications.

G3. Researcher write-ups
Candidate sources:

- Preserve author, date, URL, license/permission, and attribution.
